# Client platforms: React Native and web evidence

Checked **2026-10-22** against primary documentation and maintainer sources. Versions below are dated observations, not dependency selections. **Documented** means the source explicitly describes the capability or restriction; **inference** means an implication for Polydays; **prototype check** means application behaviour has not been verified.

## Scope and current direction

The confirmed direction is **React Native with React Native for Web**, with a shared application codebase except for platform-specific code. Initial delivery includes installed Android and browser applications; macOS initially uses web, with a native host and macOS widgets in a later phase. Android widgets are also required and have a separate research round. Expo is a candidate toolchain, not a selected dependency. TypeScript, tRPC, Node.js and server-side BoxDB are confirmed. Full offline task editing and eventual multi-device server sync are required. Notifications are excluded from version one; sleep tracking and collaboration are outside scope. These are project inputs, not platform findings; see [product requirements](../product.md).

This note supplies constraints, not final choices of Expo, storage, authentication framework, macOS implementation or interaction design. The earlier React/Tauri evidence remains relevant as an alternative below; Tauri is not the chosen Android direction.

## Shared React Native source and platform boundaries

- **Documented:** React Native for Web (RN Web) renders React Native-compatible JavaScript through React DOM. React Native lists web and macOS as out-of-tree platforms, maintained outside the Android/iOS core. Sources: [RN Web introduction](https://necolas.github.io/react-native-web/docs/), [React Native platforms](https://reactnative.dev/docs/out-of-tree-platforms).
- **Documented:** React Native supports `Platform` branches and platform-specific files, including `.native` files for code shared by native targets with separate web implementations. Native modules/components connect JavaScript to platform code. RN Web's compatibility list marks native-module loading unavailable, `Keyboard` and `BackHandler` mocked, and some other APIs incomplete. Sources: [platform-specific code](https://reactnative.dev/docs/platform-specific-code), [native integration](https://reactnative.dev/docs/native-platform), [RN Web compatibility](https://necolas.github.io/react-native-web/docs/react-native-compatibility/).
- **Inference:** Domain calculations, validation, API types, sync logic, design tokens and many task-screen components can share TypeScript source. Storage, Google sign-in, sessions and lifecycle/native integration need platform implementations. Android support in a dependency does not establish web or macOS support. Shared source is feasible; a reuse percentage or entirely platform-independent app is not established. Basis: sources above.
- **Documented:** RN Web adds mouse, touch and keyboard interactions. React Native's `useWindowDimensions` updates on window-size and font-scale changes. Sources: [RN Web interactions](https://necolas.github.io/react-native-web/docs/interactions/), [window dimensions](https://reactnative.dev/docs/usewindowdimensions).
- **Inference / prototype check:** A shared design does not require an identical layout. Verify text editing, focus order, Enter/Escape, shortcuts, selection, scrolling, Android back, accessibility and resizing on the actual task screen. Menus, window lifecycle and multiple windows, if needed, require desktop integration; common components do not prove that behaviour. Basis: interaction and platform-specific API sources above.

## Browser support and Expo as an optional toolchain

- **Documented:** RN Web's documentation, headed `react-native-web@0.21.4` when checked, says it is designed/tested for recent mobile/desktop browsers. Its known-support list includes Chrome 60+, Safari/iOS Safari 10.1+, Edge 12+, Firefox ESR+ and Opera, with export-specific exceptions and possible polyfills. This is the library's list, not a tested Polydays support policy. Source: [browser compatibility](https://necolas.github.io/react-native-web/docs/browser-compatibility/).
- **Inference:** Actual browser support also depends on selected storage, authentication, service workers and build dependencies. RN Web rendering compatibility alone cannot establish those capabilities. Test current Chrome/Android Chrome, Safari/macOS Safari and Firefox before setting a product support floor. Basis: the compatibility source and storage/authentication sources below.
- **Documented:** Expo supports web builds using RN Web; web-only React DOM components are possible but do not render on native targets. Development builds include custom native libraries and can be built locally or through EAS. Expo Go has a fixed set of native libraries. Sources: [Expo web](https://docs.expo.dev/workflow/web/), [custom native code](https://docs.expo.dev/workflow/customizing/).
- **Documented version constraint:** Each Expo SDK targets a particular RN version. The current matrix lists SDK 58 → RN 0.88, SDK 57 → RN 0.86, SDK 56 → RN 0.85, all with RN Web 0.21.0. This does not establish compatibility with the separately released RN macOS 0.83 line below. Source: [Expo version matrix](https://docs.expo.dev/versions/latest/#each-expo-sdk-version-depends-on-a-react-native-version).
- **Inference:** Expo could provide Android/web tooling without replacing the proposed Node.js/BoxDB/tRPC server. Expo Router, EAS hosting and API routes are available options, not selections implied by RN. Basis: [Expo web build modes](https://docs.expo.dev/workflow/web/) and [development-build options](https://docs.expo.dev/workflow/customizing/).

## Google sign-in: RN does not remove OAuth restrictions

- **Documented:** Google prohibits authorization in developer-controlled embedded user agents. Android guidance recommends Credential Manager, blocks embedded WebViews and requires appropriate Android OAuth client configuration. **Inference:** RN itself does not solve OAuth, and a native RN interface does not exempt an embedded login WebView. Sources: [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies#use-secure-browsers), [Android best practices](https://developers.google.com/identity/siwg/best-practices#android_implementation_apps_games).
- **Documented Android path:** Credential Manager returns a Google ID token for backend authentication. Configuration includes Android package/signing identity and a server client ID as token audience. Source: [Credential Manager implementation](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation).
- **Documented RN candidates:** Expo's current guide identifies `react-native-nitro-google-signin` and `@react-native-google-signin/google-signin`. It says the former supports Credential Manager, while the latter's Credential Manager APIs are paid; the legacy Android Google Sign-In SDK is deprecated. Both require custom native code and a **development build**, and cannot run in Expo Go. These are third-party bindings, not built-in RN authentication. Sources: [Expo Google guide](https://docs.expo.dev/guides/google-authentication/), [Nitro maintainer docs](https://react-native-nitro-google-sign-in.github.io/), [Google Sign In binding docs](https://react-native-google-signin.github.io/docs/original).
- **Documented browser helpers:** Expo AuthSession provides OAuth/OIDC helpers on Android, iOS and web. Expo WebBrowser uses Android Chrome Custom Tabs. Expo says OAuth/OIDC development and testing require a development build instead of Expo Go because the application scheme must be configurable. Generic helpers do not prove that Google accepts a particular redirect scheme. Sources: [AuthSession guide](https://docs.expo.dev/guides/authentication/), [WebBrowser](https://docs.expo.dev/versions/latest/sdk/webbrowser/).
- **Documented provider constraint:** Google's desktop flow opens the system browser and supports a loopback listener with a **Desktop app** client. Loopback redirects remain supported for desktop, not Android OAuth clients; direct Google custom-scheme redirects are unsupported on Android. Public native authorization-code clients must use PKCE under RFC 8252. Sources: [desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [loopback migration](https://developers.google.com/identity/protocols/oauth2/resources/loopback-migration), [RFC 8252 §§6–8](https://www.rfc-editor.org/rfc/rfc8252).
- **Documented web path:** Google Identity Services uses a web client with registered origins/redirects. Its client script must load from Google; offline/self-hosted copies are unsupported. **Inference:** first Google sign-in requires connectivity; reopening an authorised local account offline is a separate Polydays session policy. Source: [GIS setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).
- **Documented backend responsibility:** Verify ID-token signature, audience, issuer and expiry; use Google's stable `sub` for account identity. **Inference:** different platform flows can establish one Polydays identity, but application sessions and their persistence need implementation. No choice of Better Auth or another framework follows from RN; no BoxDB auth-adapter dependency is selected here. Source: [server verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).
- **Inference / unverified alternative:** External browser → Polydays server HTTPS Google callback → app link with a short-lived, single-use, app-bound session-handoff code could be investigated. OAuth client classification, request binding, redirect interception and session transfer require design and verification. This is not a turnkey RN/Expo integration or a direct Google Android custom-scheme redirect. Basis: [web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server), [client-type policy](https://developers.google.com/identity/protocols/oauth2/policies#register-an-appropriate-oauth-client), [RFC redirect security](https://www.rfc-editor.org/rfc/rfc8252#section-8.1).

## Durable offline data, app shell and execution

- **Documented native candidate:** `expo-sqlite` supplies SQLite access and persistence across app restarts; its current reference lists Android, iOS, macOS, tvOS and web. It is an optional module, not an inherent RN database. Source: [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/).
- **Documented web distinction:** That reference recommends `expo-sqlite ~58.0.13` when checked. Web uses WASM and requires Metro WASM support and headers enabling `SharedArrayBuffer`, including COEP/COOP. **Inference:** The documented web API does not establish production suitability, browser coverage or native-equivalent durability for Polydays. Verify exact SDK/package versions, storage persistence, concurrency and recovery. Source: [SQLite web setup](https://docs.expo.dev/versions/latest/sdk/sqlite/#web-setup).
- **Prototype check:** Test SQLite isolation headers with the actual Google login. GIS documents COOP requirements for popup communication when FedCM is disabled. Do not assume a storage example's headers work unchanged with the selected sign-in flow; this is an unverified compatibility issue, not a demonstrated blocker. Sources: [SQLite headers](https://docs.expo.dev/versions/latest/sdk/sqlite/#web-setup), [GIS COOP](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid#cross_origin_opener_policy).
- **Documented browser alternative:** IndexedDB provides transactional object storage for offline applications. Browser storage has quotas; best-effort data can be evicted. `navigator.storage.persist()` requests persistence and may be denied; persistence does not prevent explicit user deletion. Sources: [IndexedDB](https://w3c.github.io/IndexedDB/#introduction), [Storage Standard](https://storage.spec.whatwg.org/), [WebKit policy](https://webkit.org/blog/14403/updates-to-storage-policy/).
- **Inference:** Native SQLite and browser IndexedDB could implement one application storage contract without sharing an engine or queries. Tasks and pending changes need an atomic local write before success is reported. Native macOS needs a verified module; Tauri SQLite would have another bridge. These are consequences of offline durability and module boundaries, not a persistence selection. Basis: storage sources above and macOS/Tauri sources below.
- **Documented:** Expo's PWA guide requires explicit service-worker setup for offline resources and describes cache-update pitfalls. Service workers are event-bound and may be terminated while idle or over execution limits. Background Sync defers network work but has limited browser support. Sources: [Expo PWA guide](https://docs.expo.dev/guides/progressive-web-apps/), [service-worker lifetime](https://w3c.github.io/ServiceWorker/#service-worker-lifetime), [Chrome Background Sync](https://developer.chrome.com/blog/background-sync).
- **Inference:** Cached tasks alone cannot start an unloaded web app offline. Cache the application shell/assets and required routes; test shell/database upgrades together. Foreground reconnect and reopening must recover pending changes independently of background facilities. An unvisited device cannot be assumed to have an offline shell or account data. Basis: PWA/service-worker and storage sources above.
- **Documented optional native execution:** Expo BackgroundTask uses Android WorkManager; periodic work has a 15-minute minimum interval and OS-controlled execution. Force-stop/vendor behaviour matters. **Inference:** RN/Expo does not guarantee immediate closed-app sync on reconnect. Closed-app expectations remain a product decision; notification research is unnecessary for version one. Source: [BackgroundTask constraints](https://docs.expo.dev/versions/latest/sdk/background-task/).

## Installed macOS paths: alternatives, no selection

### React Native macOS: native desktop target

- **Documented:** Microsoft's `react-native-macos` is a separate out-of-tree implementation. Native modules/components use AppKit instead of UIKit; setup creates a macOS Xcode workspace with separate build/run commands. Sources: [introduction](https://microsoft.github.io/react-native-macos/docs/intro), [native development](https://microsoft.github.io/react-native-macos/docs/guides/native-development), [setup](https://microsoft.github.io/react-native-macos/docs/getting-started).
- **Documented version snapshot:** GitHub marks **`react-native-macos@0.83.0`**, released September 30, as Latest when checked. Its release note says it syncs to **RN 0.83.10**. Setup requires matching RN/RN macOS minor versions; patch versions may differ. The setup example still uses 0.81.2 and directs readers to current releases. Sources: [0.83.0 release](https://github.com/microsoft/react-native-macos/releases/tag/react-native-macos@0.83.0), [setup](https://microsoft.github.io/react-native-macos/docs/getting-started), [versioning](https://microsoft.github.io/react-native-macos/docs/contributing/versioning).
- **Documented:** Microsoft labels Expo-module support on macOS **experimental**. Expo describes adding macOS support through podspecs and platform-specific code; iOS-first native APIs generally do not become compatible through aliases alone. Sources: [installing Expo modules](https://microsoft.github.io/react-native-macos/docs/guides/installing-expo-modules), [Expo additional platforms](https://docs.expo.dev/modules/additional-platform-support/).
- **Inference / prototype check:** One dependency graph with the newest Expo SDK cannot be presumed compatible: observed RN versions differ. Verify a pinned combination or independently versioned target builds sharing source packages. Check each native dependency's macOS and architecture support, especially database and authentication. This does not establish that RN macOS is unusable. Basis: version/module sources above.
- **Documented authentication options:** Google offers an iOS/macOS native sign-in SDK. The RN Google Sign In maintainer documents macOS support in its paid version; that does not prove compatibility with a selected RN macOS build. A native binding or desktop browser flow remains integration work. Sources: [Google SDK](https://developers.google.com/identity/sign-in/ios/start-integrating), [RN binding scope](https://react-native-google-signin.github.io/docs/original), [desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

### RN Web static build inside Tauri: web-rendered desktop target

- **Documented:** Tauri accepts static HTML/CSS/JavaScript/WASM assets and does not natively run SSR. macOS uses system WKWebView/WebKit and supports an application bundle. Rust is required for development. Sources: [frontend contract](https://v2.tauri.app/start/frontend/), [WebView runtime](https://v2.tauri.app/reference/webview-versions/), [macOS bundle](https://v2.tauri.app/distribute/macos-application-bundle/), [prerequisites](https://v2.tauri.app/start/prerequisites/).
- **Inference:** A static RN Web export could reuse the web task interface inside a macOS Tauri shell. It would render through React DOM/WKWebView, not RN macOS/AppKit, and use Tauri plugins/commands rather than Android RN native modules. No official turnkey RN Web/Tauri compatibility guarantee was established here. Prototype the export, routes/assets and adapters. Basis: RN Web rendering and Tauri frontend sources above.
- **Documented building blocks:** Tauri SQL exposes SQLite on macOS and Android; Opener launches external URLs; Deep Linking supports configured desktop schemes. macOS deep-link testing requires a bundled app installed in `/Applications`. These do not constitute complete Google authentication or sync. Sources: [SQL](https://v2.tauri.app/plugin/sql/), [Opener](https://v2.tauri.app/plugin/opener/), [Deep Linking](https://v2.tauri.app/plugin/deep-linking/).
- **Inference:** This path shares the browser renderer without requiring RN macOS versions for desktop UI, while adding Rust builds, WebKit compatibility and storage/session/desktop adapters. Google authorization must still leave the embedded WebView. RN macOS instead shares RN components with native desktop rendering, with its own module/version work. These are tradeoffs to validate, not a ranking. Basis: both paths and Google policy above.

### Earlier all-Tauri alternative and browser installation

- **Documented / context:** Tauri 2 also supports Android. Its prerequisites include Android SDK/NDK/JDK and Rust targets; custom Android plugins use Kotlin/Java. Earlier evidence therefore still supports a shared web frontend in Android/macOS shells as a technically available alternative, without superseding the user's RN direction. Sources: [Tauri platforms](https://v2.tauri.app/start/), [mobile prerequisites](https://v2.tauri.app/start/prerequisites/), [mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/).
- **Documented / context:** Expo documents installable PWAs as a desktop option. That retains browser storage/lifecycle constraints, not a native macOS bundle. Whether it satisfies any future installed-macOS requirement is a product decision. Source: [PWA guide](https://docs.expo.dev/guides/progressive-web-apps/).

## tRPC and server boundary

- **Documented:** tRPC supplies typed API calls and TanStack Query integration. TanStack separately documents persisted offline mutations, hydration and resumption; functions cannot be serialized, so default mutation functions are needed after reload. Sources: [tRPC](https://trpc.io/docs/), [Query integration](https://trpc.io/docs/client/tanstack-react-query/usage), [persisted mutations](https://tanstack.com/query/latest/docs/framework/react/guides/mutations#persisting-offline-mutations).
- **Inference:** tRPC can transport a sync protocol but does not itself provide durable client storage or multi-device conflict semantics. Pending changes, operation identity/deduplication, retry after lost acknowledgements, incremental download, deletion handling and preservation of conflicting versions remain application work or need a separately evaluated sync layer. RN/RN Web do not change this boundary. Basis: documented transport/cache capabilities and project offline/conflict requirements. This round does not validate BoxDB as a client database or select an authentication framework/adapter.

## Remaining platform facts to establish with prototypes

These checks are **not performed** and do not select final designs. Their basis is the documented constraints above:

1. Pin an Android/RN Web toolchain; build an installed Android release and deployed browser app from one task screen. Verify touch, keyboard/focus, back navigation, responsive/window behaviour, accessibility and routing in intended browsers.
2. Prove Google login in a development build and signed release, not Expo Go. Check real signing configuration, cancellation, cold/warm return-to-app, token audience/identity and session persistence. Include deployed isolation headers and popup/redirect configuration if testing web SQLite.
3. For each storage adapter, atomically persist an edit/pending change, terminate/reopen offline, upgrade schema/assets, exhaust quota, deny persistence and use two tabs/windows. Establish browser SQLite persistence/recovery and coverage; establish exact native macOS module compatibility.
4. Build each macOS candidate as an installed bundle with the task UI. Test login, database persistence, menus/shortcuts, resize and lifecycle. RN macOS needs a proved version/module set; Tauri needs a proved static export and WKWebView/plugin integration. Neither path is validated here.
5. Edit offline on two devices, reconnect, lose an acknowledgement, retry and create edit/edit or delete/edit conflicts. Verify acknowledged edits survive and retries do not duplicate them. Test foreground/reopen recovery first; measure OS background behaviour if closed-app sync is required.
