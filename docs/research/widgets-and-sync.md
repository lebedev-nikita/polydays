# Widgets and offline synchronisation

Checked **2026-10-22** against official documentation and maintainer source. **Documented** describes platform/library behaviour; **inference/proposal** describes an application design; **prototype check** remains unverified. This supplements [client-platform evidence](client-platforms.md), rather than selecting another client stack.

Project inputs: [product requirements](../product.md) confirm shared React Native/RN Web source, TypeScript + Node.js + BoxDB + tRPC, installed Android and web first, native macOS later. Expo remains a candidate. Platform-specific UI, persistence and sync bridges are permitted; duplicated task/schedule semantics are not. Android widgets and future macOS widgets must participate in sync. Widget content/actions remain product questions; completion below is a capability/design example, not accepted widget scope. Notifications are excluded.

## Evidence: Android rendering and the current ecosystem

- **Documented:** Android app widgets use `RemoteViews`, with a restricted set of views and no arbitrary custom views. Jetpack Glance provides Kotlin composables over the Compose runtime, translates them into `RemoteViews`, and is not directly interchangeable with ordinary Compose UI. The launcher hosts the resulting UI separately from the application. **Inference:** an RN task-screen component cannot simply become a home-screen widget. Sources: [App Widget layout restrictions](https://developer.android.com/develop/ui/views/appwidgets#create_the_widget_layout), [Glance](https://developer.android.com/develop/ui/compose/glance), [Glance rendering/state](https://developer.android.com/develop/ui/compose/glance/glance-app-widget).
- **Documented, current first-party candidate:** Expo's latest `expo-widgets` reference recommends **`~58.0.22`** and supports Android plus iOS. Android requires the `enableAndroid` config-plugin option and a native rebuild. `createWidget`/`updateSnapshot` render a subset of `@expo/ui/jetpack-compose`; Android timelines/configurable widgets are not supported by this API. The isolated `'widget'` runtime excludes RN `View`/`Text`, hooks, app context and asynchronous work. **Inference:** TypeScript/JSX authoring is possible, but widget UI is a separate platform renderer. This is not evidence of macOS support. Source: [Expo Widgets, limitations and Android section](https://docs.expo.dev/versions/latest/sdk/widgets/).
- **Documented/source inspection:** Expo's interaction listener only fires while the app process is alive. At SDK-58 source commit `4ba7bef2655f5fbd0421fa42d03a10c1935c87e5`, Android `WidgetsInteraction.handle` evaluates the button callback, saves returned widget props, emits an event and reloads. `WidgetsEvents` invokes an optional in-memory observer; this event path has no persisted replay queue. **Inference:** a self-updating checkbox/props snapshot is not a transaction updating a Polydays task and outbox; a JS listener alone cannot durably capture closed-app completion. Sources: [interaction implementation](https://github.com/expo/expo/blob/4ba7bef2655f5fbd0421fa42d03a10c1935c87e5/packages/expo-widgets/android/src/main/java/expo/modules/widgets/WidgetInteractionAction.kt), [event implementation](https://github.com/expo/expo/blob/4ba7bef2655f5fbd0421fa42d03a10c1935c87e5/packages/expo-widgets/android/src/main/java/expo/modules/widgets/WidgetsEvents.kt), [module observer lifecycle](https://github.com/expo/expo/blob/4ba7bef2655f5fbd0421fa42d03a10c1935c87e5/packages/expo-widgets/android/src/main/java/expo/modules/widgets/WidgetsModule.kt).
- **Documented third-party alternative, not a selection:** `react-native-android-widget` exposes its own `FlexWidget`/`TextWidget`, `registerWidgetTaskHandler`, `WIDGET_CLICK` with action data, and `requestWidgetUpdateById`. Its Expo plugin generates native widget configuration and requires a dev-client build. These are maintainer APIs, not proof of compatibility with Polydays' chosen SDK, database or durability requirements. Sources: [primitives](https://saleksovski.github.io/react-native-android-widget/docs/primitives/text-widget), [task handler](https://saleksovski.github.io/react-native-android-widget/docs/tutorial/register-task-handler), [clicks](https://saleksovski.github.io/react-native-android-widget/docs/handling-clicks), [update API](https://saleksovski.github.io/react-native-android-widget/docs/api/request-widget-update-by-id), [Expo integration](https://saleksovski.github.io/react-native-android-widget/docs/tutorial/register-widget-expo/).
- **Documented:** Expo development builds accept custom native modules; Expo Go has a fixed native runtime and cannot run `expo-widgets`. Config plugins apply native project changes during prebuild. **Proposal:** evaluate a native development/release build with a local module for persistence, callbacks and workers; preserve native configuration through a plugin if using generated projects. Do not assume a widget library already supplies that integration. Sources: [custom native code](https://docs.expo.dev/workflow/customizing/), [config plugins](https://docs.expo.dev/config-plugins/introduction/).

## Evidence: durable state, identity and execution limits

- **Documented:** Glance objects should be stateless; in-memory state can disappear, and the application must explicitly publish updates after data changes. Glance supports `actionRunCallback` and broadcast actions using native handlers. Broadcast receivers have a short execution window; Android recommends `goAsync()` for short asynchronous work and WorkManager for longer work. **Inference:** persisting an offline action can be independent of a mounted RN screen; network completion should not hold a receiver open. Sources: [Glance state](https://developer.android.com/develop/ui/compose/glance/glance-app-widget), [actions](https://developer.android.com/develop/ui/compose/glance/user-interaction), [receiver duration](https://developer.android.com/develop/ui/views/appwidgets/advanced#duration_of_the_update).
- **Documented:** Room provides a native SQLite repository; its documentation addresses one database instance per process and invalidation between processes. SQLite WAL allows concurrent readers but only one writer. **Inference:** JS, receiver and worker must use one coordinated local repository/schema, with transactions, migration ownership and invalidation. Being hosted by another process does not require a separate writable task database in the launcher. Independently opening one file through unrelated JS/native database wrappers is not proven safe by either library's SQLite support. Sources: [Room ownership/invalidation](https://developer.android.com/training/data-storage/room), [SQLite WAL concurrency](https://www.sqlite.org/wal.html#concurrency).
- **Documented:** `updatePeriodMillis` has a **30-minute minimum**; WorkManager periodic requests have a **15-minute minimum**, with execution subject to constraints, Doze/power management and system scheduling. Runs may be delayed/skipped; initial delay is a lower bound. One-off expedited work is quota/load limited, can fall back to ordinary work, and may require a foreground-service notification before Android 12. Neither number is a freshness bound. Sources: [widget update scheduling](https://developer.android.com/develop/ui/views/appwidgets/advanced#determine_how_often_to_update_a_widget), [WorkRequest timing, quotas and compatibility](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).
- **Documented:** WorkManager persists/reschedules work across app restarts and reboot. Force-stop is different: Android 15 cancels pending intents and disables/grays out widgets until the user launches the app again. Expo additionally notes device-vendor differences when dismissing recent apps. **Inference:** process death, recents dismissal, reboot and force-stop need separate tests; reboot persistence does not override stopped-state restrictions. Sources: [persistent work](https://developer.android.com/develop/background-work/background-tasks/persistent), [Android 15 stopped state](https://developer.android.com/about/versions/15/behavior-changes-all#enhance-stopped-states), [Expo lifecycle caveats](https://docs.expo.dev/versions/latest/sdk/background-task/).
- **Documented:** Expo BackgroundTask schedules deferrable JS tasks through native schedulers; RN Headless JS can start JS without UI, then pause it after completion. These are execution facilities, not an always-running JS process. **Inference:** neither a React effect nor an event listener supplies durable scheduling; a native outbox/worker should remain able to persist/send widget actions when the application's JS runtime is absent. Sources: [Expo BackgroundTask](https://docs.expo.dev/versions/latest/sdk/background-task/), [Headless JS](https://reactnative.dev/docs/headless-js-android).
- **Documented:** Credential Manager obtains a Google ID token; the backend validates signature, audience, issuer and expiry, and identifies the user by `sub`. This establishes identity, not background execution. **Proposal:** establish a separate Polydays session after verification. Native workers need native-accessible session renewal/storage, separate from browser cookies or JS memory. On expiry/revocation, suspend authenticated sync, retain local tasks/outbox and request reauthentication in the app; workers must not launch Google sign-in UI. An unavailable user-authentication-bound storage key must defer sync. Sources: [Google Android flow](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation), [backend verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Keystore authentication restrictions](https://developer.android.com/privacy-and-security/keystore).

## Evidence: future native macOS widgets

- **Documented:** WidgetKit uses a widget extension target and SwiftUI views, with code running separately from the containing app. App Groups provide a shared container for an app and extension. **Inference:** transactional storage and credential access still need explicit implementation/configuration. A pure website/PWA cannot itself register this native extension or access an App Group as an installed signed app. A future macOS host needs a bundled WidgetKit extension and storage/session bridge, regardless of how its main RN-derived UI renders. Sources: [extension target](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension), [App Groups](https://developer.apple.com/documentation/xcode/configuring-app-groups).
- **Documented:** Timeline entries describe predictable future displays; `WidgetCenter.reloadTimelines` requests new timelines after data changes. Reload budgets are dynamic: Apple's typical **40–70 reloads/day** for frequently viewed widgets is illustrative, not an entitlement or SLA. Reloads may be coalesced; a requested date is not a real-time deadline. Network requests can run while an extension is active, with background URLSession support for appropriate requests, but resources/lifetime are limited. Sources: [timeline/reload budgets](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date), [widget networking](https://developer.apple.com/documentation/widgetkit/making-network-requests-in-a-widget-extension).
- **Documented:** Buttons/toggles use AppIntents to act without launching the foreground app. By default an ordinary `AppIntent` executes in the widget-extension process. Persist required state before returning from `perform()`; the interaction triggers a timeline reload. **Proposal:** use the same durable command/outbox contract through an App Group repository, with native transport/retry integration; do not require the future RN window to be open. Sources: [AppIntent execution and persistence](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities).

## Architecture proposal for the parent to evaluate

These are consequences/design options based on the evidence above, not platform guarantees or a final sync specification.

1. **One semantic core, explicit adapters.** Share pure TypeScript task, occurrence, polyday, timezone/DST, priority and conflict rules between clients and Node. Share versioned command/projection schemas and conformance fixtures with Kotlin/Swift. Keep widget layouts, lifecycle, credentials and persistence native. Do not independently implement recurrence or reassignment inside each widget. tRPC has a documented HTTP RPC protocol: a native worker can call a deliberately small JSON-compatible sync procedure, with contract tests for serialization/auth/errors; it cannot directly use TypeScript type inference. Source: [tRPC HTTP specification](https://trpc.io/docs/rpc).
2. **One native repository boundary.** On Android, expose a native transactional repository to RN through a module; receiver and WorkManager use it directly. Room/SQLite is a candidate, not a selected wrapper. Persist task/operation state, pending commands, acknowledgements/cursor and widget projections under one schema/migration authority. Use a lease or equivalent coordination for foreground/background drains; OS scheduler deduplication alone is insufficient. Web implements the same contracts with browser persistence; server BoxDB is a separate store. Future macOS needs equivalent cross-process coordination in its App Group.
3. **If completion is in scope, commit before claiming success.** A native callback records `SetCompleted(true)` for a stable task/occurrence ID, account, operation ID, causal/base version and observed timestamp; atomically save its local completion overlay plus outbox entry. Preserve assigned-polyday identity; do not complete whichever occurrence is current when the worker eventually runs. Atomically associate a widget action token with its persisted operation ID so repeated delivery reuses that identity; setting a value avoids retrying a toggle into its opposite. Backlog completion, moves and other semantic actions require commands produced by the common core, not ad hoc native rules.
4. **Native transport owns retry, not React.** After commit, refresh from durable local state and enqueue network-constrained native work. Drain persisted operations with idempotent server deduplication and durable acknowledgements. Commit incoming deltas, conflicts and cursor together; preserve pending overlays instead of overwriting them with a remote snapshot. Keep enough operation history for app replay even when transport has already received an acknowledgement. Recover a crash between commit and enqueue by scanning pending work on startup, scheduled maintenance and subsequent widget callbacks. Expedited work is optional and subject to the notification/version restrictions above; ordinary work is the baseline. No perpetual foreground service, exact alarm or battery exemption is required by this proposal.
5. **Prepared projections avoid another domain engine.** The shared TS core can prepare widget data, explicit occurrence IDs and future validity intervals in the app; the same core on Node can return refreshed projections during native sync. Native code selects an interval and applies narrow pending completion overlays, rather than regenerating recurrence or resolving domain conflicts. If offline edits invalidate a projection, rebuild it through the common core. A finite prepared horizon must be explicit: after it expires, show dated cached information/unavailability until regeneration. Unlimited offline widget recalculation would require a verified way to invoke the common core without the foreground app; do not silently promise it from a cache.
6. **Separate time-based rendering from network sync.** Local widget refresh must not require connectivity. On each permitted execution, choose the projection for now using the confirmed account timezone/schedule version, including midnight-crossing intervals and sleep gaps. Request a local refresh near the next boundary, and update on app resume, local writes and received sync data. Android scheduling cannot guarantee that the old list disappears at the polyday boundary; even a newly appearing “stale” badge requires an execution opportunity. Include the displayed polyday/range and data timestamp from the outset. WidgetKit timelines can predeclare future boundaries, but still do not establish an exact deadline or freshness of remote data. Foreground/reopen sync is the dependable recovery path; closed-app reconnect and remote-device updates have no bounded delivery time.

## Prototype checks before choosing integrations

No application prototype was built in this research round. Validate the following on a pinned native development build and release build:

- Native completion with RN JS absent and network off; kill before/after local commit, enqueue, send and acknowledgement; restart and verify one occurrence completed, no lost command and eventual server agreement. Repeat deliveries and simultaneous widgets must not toggle state or erase pending work.
- A second device edits/completes/deletes the same task while this device is offline; verify automatic independent-field merging and preservation of incompatible versions. Exercise schedule/series/timezone changes and stale occurrence references.
- Concurrent RN writes, widget callbacks and worker drains; migration/recovery with an older cached widget and interrupted process; disk-full/locked-store errors; account switch/logout and session refresh/revocation without credential leakage or lost outbox entries.
- Render/refresh with connectivity disabled at a polyday boundary, overnight, during sleep gaps and DST changes; exhaust prepared projections. Measure delays under Doze, battery saver, reboot, recents dismissal and force-stop on the actual Android device. A simulator success does not prove vendor behaviour.
- Confirm the selected Expo/native widget path can call the repository and publish new content without a JS listener or development server. Check generated manifest/receiver/worker configuration and rebuild reproducibility. Reject integrations that demonstrate only persisted checkbox props.
- In the later macOS phase, prove signed host/extension App Group and credential access, concurrent persistence, AppIntent offline completion, timeline invalidation and delayed networking with the app window closed. Treat current Expo Android/iOS APIs as no evidence of this compatibility.
